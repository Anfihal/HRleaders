# HRleaders Web — Vue, Vite и Nuxt UI

Самостоятельное веб-приложение в `vite-app/`, рядом с Flutter-клиентом. Веб-клиент использует Vue 3, Vue Router, Vite, Nuxt UI и Tailwind CSS 4. Nuxt UI здесь подключён как библиотека компонентов для обычного Vue/Vite-приложения; Nuxt framework для запуска не требуется.

## Архитектура

```text
src/
  main.ts                 Создание Vue-приложения, router и Nuxt UI plugin
  App.vue                 Корневой layout, восстановление сессии, demo-индикатор
  router.ts               Маршруты, проверка авторизации и ролей
  session.ts              Выбор demo/HTTP адаптера и состояние пользователя
  api.ts                  HrApi-контракт, HTTP-клиент и преобразование DTO
  demo.ts                 Локальная реализация HrApi и демонстрационные данные
  types.ts                Общие типы пользователей и доменных сущностей
  components/
    AppShell.vue          Навигация для desktop/mobile и выход из аккаунта
    RedFlagGame.vue       Необязательная игра в форме кандидата
  views/                  Страницы landing, candidate и HR
  app.css                 Tailwind/Nuxt UI imports, тема и адаптивные стили
public/api/openapi.json   Снимок OpenAPI-контракта проекта
```

### Границы приложения

- Страницы обращаются к общему интерфейсу `HrApi`, а не напрямую к `fetch`. Реализации выбираются в `src/session.ts`: `DemoHrApi` или `HttpHrApi`.
- `DemoHrApi` хранит демонстрационную сессию и состояние приложения в browser `localStorage` под ключом `hrleaders-vite-demo-v1`. Это локальные вымышленные данные, не синхронизируемые с сервером.
- `HttpHrApi` отправляет HTTP-запросы к API, преобразует часть snake_case DTO в типы интерфейса и передаёт cookies (`credentials: 'include'`). Access token, если его вернул API при входе, живёт только в памяти страницы.
- `router.ts` ограничивает маршруты ролями `candidate` и `hr`. Это UX-защита; backend обязан самостоятельно проверять авторизацию и права на каждом защищённом endpoint.
- Nuxt UI предоставляет UI-компоненты (`UButton`, `UCard`, формы, badges, modal, progress, alert и др.); Lucide-иконки поставляются через `@iconify-json/lucide`.
- Backend в этой папке не реализован. `public/api/openapi.json` описывает контракт, но сам по себе не подтверждает наличие, готовность или совместимость работающего сервера.

## Функционал

### Общие сценарии

- Публичная landing-страница, вход, регистрация кандидата и HR-рекрутёра.
- Раздельная навигация и маршруты для кандидата и HR.
- Валидация форм, состояния загрузки/ошибок и адаптивная компоновка для узких экранов.
- Сворачиваемая мини-игра «прыжки через красные флаги» в форме регистрации кандидата. Игра не влияет на регистрацию, авторизацию или оценку кандидата; цикл анимации и обработчики завершаются при закрытии компонента.

### Кабинет кандидата

- Просмотр и изменение профиля, специализации, локации, навыков, формата работы, зарплатных ожиданий и готовности получать предложения.
- Каталог тестов, назначения от рекрутёров, прохождение вопросов, сохранение ответов и просмотр результата.
- Просмотр и принятие/отклонение входящего предложения; при отказе указывается причина.
- Раздел совпадений показывает принятые предложения — отдельного endpoint совпадений в текущем API-клиенте нет.

### Кабинет HR

- Поиск открытых для предложений кандидатов по навыку и грейду, просмотр профиля и сохранение кандидата в отслеживание.
- Назначение кандидату оценки; просмотр списка кандидатов, статусов и доступного результата.
- Создание и закрытие вакансий.
- Отправка предложений из профиля кандидата с выбором активной вакансии и зарплаты.
- Сводные показатели найма.
- HR Assistant использует локальные явно демонстрационные шаблоны только в demo-режиме. В live-режиме запрос отклоняется понятной ошибкой, потому что серверный endpoint не подключён.

### Известные ограничения текущей версии

- Переписка пока является информационной страницей: messaging API не подключён.
- Регистрация через live API предполагает контракт `POST auth/register`; реальный сценарий подтверждения email, восстановления пароля, MFA и управления сессиями в интерфейсе не реализован.
- Demo-вход: `candidate@demo.hrleaders.example` и `hr@demo.hrleaders.example`, пароль `Demo12345`. Эти учётные данные предназначены только для локальной демонстрации.
- Live API-клиент и OpenAPI-файл должны быть сверены с фактическим backend перед production. В частности, набор DTO, фильтров, статусов и response body зависит от серверной реализации.
- JWT access token хранится в памяти и теряется после полной перезагрузки. Для восстановления входа между перезагрузками backend должен использовать безопасную cookie-сессию либо требуется отдельная согласованная реализация refresh-токена. Не помещайте долгоживущий токен в `localStorage`.

## Требования

- Node.js, совместимый с установленными версиями Vite и Vitest (рекомендуется актуальный поддерживаемый LTS).
- npm.
- Backend HRleaders для live-режима; для демонстрации сервер не нужен.

Зависимости зафиксированы lock-файлом `package-lock.json`. В CI и воспроизводимых сборках используйте `npm ci`; `npm install` оставьте для обновления зависимостей.

## Установка и запуск

В PowerShell:

```powershell
Set-Location C:\home\Flutter\hr-flutter-app\vite-app
npm ci
npm run dev
```

Откройте локальный адрес, напечатанный Vite в терминале. По умолчанию запускается demo-режим. Для входа можно использовать демонстрационные email и пароль из раздела «Функционал» либо зарегистрировать локального demo-пользователя. Состояние demo хранится в браузере; чтобы начать заново, очистите site data/local storage для локального адреса приложения.

Проверки и production preview:

```powershell
npm test
npm run build
npm run preview
```

`npm run build` сначала выполняет `vite build`, который генерирует типовые декларации Nuxt UI, затем запускает `vue-tsc --noEmit`. Результат сборки находится в `dist/`.

## Настройка live API

### 1. Подготовьте backend

До переключения проверьте на тестовом окружении, что backend запущен и предоставляет совместимые endpoints согласно `public/api/openapi.json` и запросам в `src/api.ts`. Одного OpenAPI-файла недостаточно: нужен развернутый сервер, тестовые пользователи и данные.

Настройте на сервере:

- CORS для точного origin веб-клиента и credentials, если frontend и API работают на разных origin. Нельзя сочетать `Access-Control-Allow-Credentials: true` с wildcard origin.
- Авторизацию и RBAC на каждом endpoint, независимо от Vue Router guard.
- HTTPS в staging/production, корректные cookie attributes (`Secure`, `HttpOnly`, `SameSite`) и защиту от CSRF, если авторизация использует cookies.
- Стабильные форматы ошибок и JSON DTO, соответствующие mapper-ам `HttpHrApi`.

### 2. Переключите адаптер с mock на HTTP

Для локальной работы с backend, доступным на `http://localhost:8000`:

```powershell
$env:VITE_DEMO = "false"
$env:VITE_API_PROXY_TARGET = "http://localhost:8000"
npm run dev
```

`VITE_DEMO=false` выбирает `HttpHrApi`; любое иное или отсутствующее значение оставляет включённым demo adapter. При стандартном `VITE_API_BASE_URL` запросы идут на `/api/v1/`, а Vite проксирует префикс `/api` к `VITE_API_PROXY_TARGET`. Пример: `/api/v1/auth/login` отправляется прокси на backend как `/api/v1/auth/login`.

Чтобы обратиться к API напрямую, задайте его URL:

```powershell
$env:VITE_DEMO = "false"
$env:VITE_API_BASE_URL = "https://api.example.com/api/v1/"
npm run dev
```

В этом варианте backend должен разрешать origin frontend в CORS и credentials, если сессия основана на cookies. Base URL задаётся с `/` на конце (клиент нормализует завершающий slash).

Для настройки через файл создайте `vite-app/.env.local`:

```dotenv
VITE_DEMO=false
VITE_API_BASE_URL=/api/v1/
VITE_API_PROXY_TARGET=http://localhost:8000
```

Локальные `.env.local`/`.env.*.local` не следует коммитить. Переменные с префиксом `VITE_` встраиваются в публичный клиентский bundle: не размещайте в них пароли, приватные ключи, секреты или серверные credentials. Для production настройте значения в среде сборки и соберите приложение заново — runtime-подмена этих переменных в готовом `dist` не предусмотрена.

### 3. Войдите и проверьте сквозные сценарии

Live-режим не использует локальные demo-учётные записи. Войдите через пользователя, созданного на backend, и проверьте как минимум:

1. `auth/login`, восстановление сессии через `auth/me`, выход через `auth/logout` и регистрацию, если она включена на сервере.
2. Чтение и изменение профиля; поиск кандидатов по фактически поддерживаемым сервером фильтрам.
3. Назначение, начало, сохранение ответов и завершение оценки, включая выдачу backend достоверного результата.
4. Отслеживание кандидата, создание/закрытие вакансии, отправку предложения и ответ кандидата.
5. Отказы API, истечение/отсутствие сессии, права ролей и CORS в браузере.

Сравните ответы сервера с преобразованиями в `HttpHrApi`: клиент ожидает для login/register объект с `user` (`id`, `email`, `full_name`, `role`, необязательное `company_name`) и необязательным `access_token`; для большинства сущностей используются snake_case поля, например `candidate_id`, `followed_at`, `score_percent`, `salary_from` и `created_at`.

### Сессия и безопасность

HTTP-клиент отправляет `credentials: 'include'`. При успешном login/register он также сохраняет возвращённый `access_token` только в памяти и прикладывает его как `Authorization: Bearer …`. После перезагрузки страницы этот bearer token теряется. `GET auth/me` может восстановить пользователя без повторного входа только если сервер поддерживает соответствующую cookie-сессию. Уточните контракт своего backend; не считайте наличие frontend role guard заменой серверной авторизации.

Live-режим отключает UI-демо-вход и локальные mock-ответы Assistant. Вакансии, предложения, поиск и оценки будут работать только если соответствующие endpoints действительно доступны серверу. Переписка пока не подключена.

## Сборка и размещение

Соберите оптимизированный SPA bundle:

```powershell
npm run build
```

Разместите содержимое `dist/` за статическим HTTPS-хостингом/CDN. Настройте fallback неизвестных путей приложения на `index.html` для history-маршрутов Vue Router. API можно разместить за тем же origin и маршрутизировать `/api` на backend либо задать публичный `VITE_API_BASE_URL` при сборке. Настройте cache headers для assets с хешированными именами и не кэшируйте HTML дольше, чем нужно для своевременного обновления приложения.

В production сначала проверьте сборку и live-конфигурацию на staging; не включайте mock-режим как production fallback. Если backend недоступен или DTO несовместимы, приложение должно показывать ошибку, а не переключаться незаметно на локальные demo-данные.
